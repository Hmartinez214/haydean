Reading this honestly

The cutover changed two things at once: the protocol (NFS→BeeGFS) and the disks (one 7200rpm HDD → four SSDs). Comparing /home against BeeGFS would credit BeeGFS for the SSDs. So the headline compares BeeGFS against NFS on the very same SSDs, same three client nodes, identical mdtest settings — measured at /haydean just before and just after the cutover. That isolates the protocol.

Bar = mean speedup across the rank sweep; the pale line spans min–max. Right of the dashed line, BeeGFS wins. Directory creation is absent because every matched point failed the reliability check below.

What this means

  • BeeGFS is genuinely faster, but the SSDs did most of the work. On identical hardware BeeGFS creates files 1.8× faster and removes them ~3× faster. The 156× gap against /home is mostly the disks.
  • BeeGFS keeps scaling; NFS plateaus. NFS-on-SSD file creation flattens at ~4,000/sec once the single server saturates. BeeGFS reaches ~9,028/sec by spreading metadata across two servers and data across four.
  • Stat-heavy work is where BeeGFS wins least. File stat is only 1.3–1.7× better — reads were never NFS's weak point.
  • /home is now the bottleneck. Still NFS on one 7200rpm HDD at 58 creates/sec, and completely flat from 4 to 48 ranks — adding clients buys nothing. Conda environments, pip installs and job scripts all live there. Moving that workload onto BeeGFS is the next real win.

Method

  • mdtest 4.1.0, 64 files/rank, 2 iterations, stat phase strided by ranks-per-node so a rank stats files created on a different node.
  • Zero-byte files: this is a pure metadata benchmark. It says nothing about bandwidth — use ior for that. mdtest's "File read" row is excluded entirely, since with no payload it only measures open/close.
  • One job at a time (--exclusive + Slurm singleton dependency); concurrent jobs would contend for the same servers.
  • Idle verified before and after: no other users' jobs, no interactive users, server disks at ~0% utilisation. An earlier attempt was discarded because the login node had ten active users with its disk 92–98% busy.
  • NFS-on-SSD figures come from /haydean shortly before the BeeGFS cutover — same path, same parameters, same client set, so they compare directly.
  • Reproduce with ./submit_compare.sh && python3 compare_results.py in ~/storagebenchmarks.
